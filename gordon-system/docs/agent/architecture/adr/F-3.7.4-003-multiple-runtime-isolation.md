# ADR: Multiple-Runtime Isolation Mechanism

## Decision

**Status**: APPROVED  
**Date**: August 3, 2026  
**Phase**: 3.7.4  

### Summary

Gordon will implement multiple-runtime isolation through **assembly-scoped state isolation** using unique identifiers and immutable data structures. Each `RuntimeAssembler` instance maintains its own assembly session state through:

1. Unique `AssemblyId` per assembler instance
2. Unique `BootSessionId` per assembly attempt  
3. Immutable request/response objects that cannot be shared between runtimes
4. Thread-local locking for single-use pattern enforcement

This approach provides **isolation by construction** without introducing distributed-system mechanisms.

class AssemblyId:
    """Unique assembly session identifier."""
    value: str
    
    @classmethod
    def generate(cls) -> "AssemblyId":
        return cls(value=str(uuid.uuid4()))

    """Runtime boot session identifier."""

## Alternatives Considered

### Alternative 1: Distributed Lease Manager (REJECTED)
**Rationale**: Introducing distributed-system mechanisms like fencing tokens, generation IDs, or lease managers is disproportionate for a single-runtime, in-process architecture.

**Rejected because**:
- Gordon is explicitly designed as single-runtime, in-process
- No evidence of concurrent runtime assembly use case
- Would introduce unnecessary complexity and synchronization overhead

### Alternative 2: Global Registry with Locks (REJECTED)
**Rationale**: A global registry to track active assemblies would violate the authority ownership principle.

**Rejected because**:
- Creates centralized coordination point
- Introduces shared mutable state
- Contradicts immutable composition principle

### Alternative 3: Runtime Pool (DEFERRED)
**Rationale**: Pool-based allocation could provide isolation but changes runtime lifecycle semantics.

**Deferred because**:
- Not required for Phase 3.7.4
- Should be evaluated as future extension (FUTURE_EXTENSION)

## Decision Justification

### Why This Approach?

1. **Single-Runtime Assumption**: Gordon is explicitly single-runtime, in-process
2. **Isolation by Construction**: Python's object model + immutable dataclasses provide natural isolation
3. **No Distributed Complexity**: UUIDs and instance isolation are sufficient for in-process use
4. **Maintainability**: Simple, obvious isolation without distributed-system overhead

### When Would This Change?

This approach would need re-evaluation if:
- Gordon transitions to multi-runtime or distributed architecture
- Runtime instances must share state intentionally
- External runtime coordination becomes required
